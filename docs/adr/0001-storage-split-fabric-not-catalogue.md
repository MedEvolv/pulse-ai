# Storage backs the mutable fabric, not the deterministic catalogue

## Context

Pulse conflates two stores under the word "database": the **deterministic catalogue**
(leads/appointments/leakages/evidence generated by `engine.py` from a fixed seed, read-only)
and the **mutable fabric** (interventions, closure proofs, model budget — the only things
that change and the only things any adapter persists today).

## Decision

The Postgres adapter — and the shared unified database — back the **mutable fabric only**
(`core.intervention`, `core.closure_proof`, `core.evidence`, model budget/cache). The
deterministic catalogue stays generated by `engine.py` and is **never** written to
`pulse.lead` / `pulse.leakage` / etc. Cross-product alignment with ReputationOS happens at
the **intervention** level, which the fabric already unifies.

## Why

- The intervention/closure fabric is the alignment keystone (per
  `decision--pulse-ai-product-convergence-v0.1`), and it is the only thing already behind the
  storage interface — so the adapter is a drop-in.
- The catalogue is deterministic and regenerable; persisting thousands of synthetic rows on
  every deploy adds sync risk and contradicts Pulse-00's "engine is the single source of
  truth" rule.
- Full catalogue unification (writing `pulse.*`) earns its keep only when real, non-synthetic
  leads arrive — which is also the DPDP / provisioning trigger already gated in
  `docs/unified-database/README.md` §7.

## Consequences

SQL joins of Pulse leakages ↔ ReputationOS tickets are not possible until full unification;
until then, cross-product analytics join at the intervention level (`core.intervention_feed`).
